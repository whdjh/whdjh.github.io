## 왜 공부하게 되었나

App Router 도입 후 **RSC(React Server Component)**, **SSR**, **CSR**의 역할과 경계를 헷갈려서, **번들 비대화**와 **상태 보존** 문제가 반복됐다.  
원리부터 정리해서 구조를 단순히 하려고 공부를 시작했다.

---

## 문제 상황

- **`'use client'`**를 중간 레이어에 두다 보니, 그 **하위 트리 전체**가 클라이언트 번들로 묶여 **번들 크기 증가·로딩 지연**이 발생했다.
- **클라이언트 컴포넌트**에서 **서버 컴포넌트**를 import하려다 **빌드 에러**나 **제약**이 자주 생겼다.

---

## 공부 내용

### 무엇이 서버 컴포넌트인가?

**서버에서** 컴포넌트를 렌더링한 뒤, 그 결과를 **클라이언트로 전달**하는 컴포넌트다.

### 특징

1. **리렌더링되지 않는다** (클라이언트에서 다시 그리지 않음)
2. **서버 리소스**에 접근 가능하다 (파일시스템, DB 등)
3. **JavaScript 번들에 포함되지 않는다** → 제로 번들 사이즈
4. **자동 코드 스플릿팅**: import되는 컴포넌트가 자동으로 스플릿 포인트가 됨 → `lazy` 명시 불필요
5. **사용자 인터랙션**은 제공하지 못한다 (클라이언트 컴포넌트로 보완)

### SSR과의 공통점·차이점

**공통점**: 둘 다 **서버에서 렌더링**된다.

**차이점**

| 구분 | SSR | 서버 컴포넌트(RSC) |
|------|-----|---------------------|
| 역할 | 초기 **HTML** 생성 | 컴포넌트를 **번들에 넣지 않고** 서버에서 실행 |
| 번들 | 컴포넌트 코드가 **JS 번들에 포함** | **번들에 포함 안 됨** |
| 리소스 접근 | 최상위 페이지 등 **함수 단위**에서 백엔드 리소스 접근 | **페이지 레벨과 무관하게** 백엔드 리소스 접근 |
| refetch 시 | 새 **HTML**을 받아 다시 렌더 → **상태 보존 불가** | **RSC Payload**로 받아와 **상태 보존 가능** |

---

### React 서버 컴포넌트를 어떻게 쓰는가?

Next.js(App Router)에서는 **모든 컴포넌트가 기본적으로 서버 컴포넌트**다.  
클라이언트 컴포넌트도 쓰고, Hook도 쓰고 싶다면 **`'use client'`** 지시문을 사용한다.

> **어떤 기준으로 나눌까?**
> 1. **상태, 이펙트**가 필요하면 → **클라이언트 컴포넌트(CC)**
> 2. 그 외 → **서버 컴포넌트(SC)**

---

### 경계를 기준으로

- **전부 서버 컴포넌트**라면 문제가 없지만, **중간에 `'use client'`**가 있으면 그 아래는 **클라이언트 경계(Client Boundary)**가 된다.
- 해당 클라이언트 컴포넌트가 **리렌더**돼도, 그 **하위에 있는 서버 컴포넌트**는 다시 서버에서 렌더되지 않는다.
- **클라이언트 컴포넌트가 import하는 컴포넌트는 반드시 클라이언트 컴포넌트**여야 한다.  
  → 그래서 **Client Boundary 아래**는 전부 클라이언트 컴포넌트가 되고, 서버 컴포넌트를 쓰는 쪽에서는 **제약**이 생긴다.

**이 제약을 피하는 방법**:  
**상위를 서버 컴포넌트**, **하위를 클라이언트 컴포넌트**로 두는 구조를 우선한다.  
(클라이언트 컴포넌트가 서버 컴포넌트를 자식으로 import하는 건 불가능하므로, 반대 구조만 가능하다.)

---

## 결과

- **SSR**의 초기 HTML 렌더링과 **서버 컴포넌트**의 제로 번들링을 함께 쓰면, 더 빠른 초기 로딩과 작은 클라이언트 번들을 동시에 노릴 수 있다.
- 서버 컴포넌트와 클라이언트 컴포넌트의 **경계**를 명확히 두고, **상위 SC → 하위 CC** 구조를 지키면 번들·상태 문제를 줄일 수 있다.
