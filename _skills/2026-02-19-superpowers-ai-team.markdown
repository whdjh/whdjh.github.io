우리는 지금까지 AI(LLM)를 **'똑똑한 비서'** 정도로만 활용해 왔습니다. 채팅창 하나를 열어두고, 질문하고, 답변을 받고, 코드를 복사해서 붙여넣었죠. 하지만 프로젝트가 조금만 커져도 AI는 앞의 내용을 까먹거나(Context Window 초과), 엉뚱한 코드를 짜기 시작합니다.

이 문제를 해결하고, AI의 생산성을 극한으로 끌어올리는 방법론, 바로 **'Superpowers'** 워크플로우에 대해 이야기해 보려 합니다.

핵심은 **"생각(Brainstorming)", "공간(Git Worktree)", "조직(Agents)"** 이 3가지를 분리하는 것입니다.

---

## 브레인스토밍: 왜 바로 코딩하면 안 될까?

많은 개발자가 AI에게 "로그인 페이지 만들어줘"라고 바로 명령합니다. 하지만 이것은 **실패로 가는 지름길**입니다.

### 문맥의 한계와 환각(Hallucination)

AI는 천재적인 기억력을 가진 것 같지만, 대화가 길어지면 앞의 내용을 잊어버립니다. 바로 코딩에 들어가면 구현 도중에 "어? 아까 그 변수 뭐였지?" 하며 실수를 하거나, 없는 라이브러리를 가져다 쓰는 환각 증상을 보입니다.

### 계획 없는 코딩은 스파게티를 만든다

브레인스토밍 단계는 AI에게 **'지도'**를 쥐여주는 과정입니다.

- "어떤 기술 스택을 쓸 것인가?"
- "예외 처리는 어떻게 할 것인가?"
- "파일 구조는 어떻게 잡을 것인가?"

이 과정을 통해 `spec.md`나 `plan.md` 같은 **설계 문서**를 먼저 만들어야 합니다. 이 문서가 AI에게는 진실의 원친이 되어, 코딩 중 길을 잃지 않게 해줍니다.

---

## 깃 워크트리(Git Worktree): AI를 위한 독방

설계가 끝났다면 이제 코딩을 해야 합니다. 그런데 왜 그냥 브랜치(`git checkout`)가 아니라 **워크트리**를 써야 할까요?

### 개념: 공간의 물리적 분리

`git checkout`은 내 방(폴더)의 인테리어(파일)만 싹 바꾸는 것입니다. 한 번에 한 가지 테마만 볼 수 있죠.  
반면, **`git worktree`는 내 방 옆에 똑같은 방을 하나 더 짓는 것(폴더 복제)**입니다.

### 왜 쓰는가? "문맥 오염 방지"

AI 에이전트에게 일을 시킬 때 가장 치명적인 것은 **'문맥 오염(Context Pollution)'**입니다.

- A 기능을 구현하는 에이전트가 B 기능의 파일까지 보고 있으면 헷갈려 합니다.
- 워크트리를 사용하면 `folder-ui`, `folder-api`처럼 **물리적으로 격리된 폴더**를 줄 수 있습니다.
- AI는 "이 폴더 안에 있는 것만 신경 쓰면 돼"라는 환경에서 최고의 퍼포먼스를 냅니다.

### 도대체 `git clone`이랑 뭐가 다른건데?

가장 많이 하는 오해입니다. "그냥 프로젝트 폴더를 하나 더 다운로드(Clone) 받으면 되는 거 아냐?"

| 구분 | Git Clone (폴더 복사) | **Git Worktree (작업 트리)** |
| --- | --- | --- |
| **용량** | 2배 (히스토리까지 전부 복사) | **1.01배** (소스 코드 텍스트만 생성) |
| **동기화** | 서로 남남 (Push/Pull 해야 함) | **실시간 공유** (한 몸) |
| **관리** | 설정 파일(.env 등) 다시 세팅 | 설정 공유 가능 |

- **핵심은 `.git` 폴더의 유무입니다.**
  1. **Clone:** 각 폴더가 무거운 `.git` 데이터베이스를 따로 가집니다.
  2. **Worktree:** 메인 폴더의 `.git` 데이터베이스를 **참조(Reference)**만 합니다. 그래서 워크트리 폴더에는 `.git` 폴더 대신 텍스트 파일 하나(`.git`)만 들어있습니다.

---

## 메인 에이전트와 서브 에이전트: "팀장과 팀원"

이제 공간도 마련되었으니 일을 시켜야 합니다. 여기서 등장하는 것이 **Main Agent**와 **Sub-Agent**의 개념입니다.

### 왜 굳이 나눌까?

혼자서 북 치고 장구 치고 다 하면 안 될까요? 안 됩니다. **'역할의 크기'**가 다르기 때문입니다.

- **메인 에이전트 (The Architect / PM):**
  1. **역할:** 전체 프로젝트의 `spec.md`를 이해하고, 큰 그림을 봅니다. 직접 코딩하기보다는 "어떤 일을 해야 하는지" 정의하고, 작업이 끝나면 코드를 합치는(Merge) 역할을 합니다.
  2. **비유:** 팀장급 개발자, PM

- **서브 에이전트 (The Worker / Developer):**
  1. **역할:** 전체 구조는 모릅니다. 단지 메인 에이전트가 던져준 "로그인 버튼 컴포넌트 만들어"라는 **작고 구체적인 지시**만 수행합니다. 격리된 워크트리 속에서 오직 그 임무에만 집중합니다.
  2. **비유:** 신입 개발자, 외주 개발자

이 계층 구조가 있어야 메인 에이전트가 "전체 문맥"을 놓치지 않으면서도, 디테일한 구현을 서브 에이전트에게 위임할 수 있습니다.

---

## 결론: 병렬 실행

이 모든 요소(브레인스토밍, 워크트리, 멀티 에이전트)가 합쳐지면 비로소 **Superpowers**가 발동합니다.

### 시나리오: "로그인 페이지 개발"

1. **브레인스토밍:** 나와 메인 에이전트가 대화하며 `spec.md`를 완성합니다.
2. **명령 하달 (Orchestration):** 메인 에이전트가 판단합니다. "UI 작업과 API 작업으로 나누자."
3. **환경 구축:**
   - `git worktree add ../login-ui` (UI 작업실 생성)
   - `git worktree add ../login-api` (API 작업실 생성)
4. **병렬 투입:**
   - **서브 에이전트 A**를 `../login-ui` 창에 투입.
   - **서브 에이전트 B**를 `../login-api` 창에 투입.
5. **동시 실행:** 나는 커피를 마시고 있는 동안, 두 개의 창에서 코드가 **동시에** 작성됩니다.
6. **통합:** 각 작업이 끝나면 메인 에이전트가 작업물을 수거해 `main`으로 병합합니다.

---

이것이 바로 AI 시대의 **1인 개발 팀** 운영 방식입니다.  
단순히 "코드를 빨리 짜는 것"을 넘어, **"동시에 여러 명의 개발자를 부리는 것"**과 같은 효과를 냅니다.

- **생각**은 깊게 (Brainstorming)
- **작업 공간**은 확실하게 (Git Worktree)
- **실행**은 동시에 (Sub-Agents)

---

## 부록: Git Worktree 완벽 가이드 (기술적 심층 분석)

### 작동 원리

1. **메인 저장소(Main Repo):** `Project-Main` 폴더 (여기에 진짜 데이터베이스가 있음)
2. **워크트리(Linked Worktree):** `Project-Sub` 폴더 생성
3. **연결:** `Project-Sub` 폴더 안에 `.git` 파일을 열어보면 다음과 같이 적혀 있습니다.
   `gitdir: /path/to/Project-Main/.git/worktrees/sub`
4. **결과:** `Project-Sub`에서 커밋을 하면, 마법처럼 `Project-Main`의 Git 기록에도 즉시 남습니다. **몸은 떨어져 있지만 영혼은 공유하는 상태**입니다.

### 실전 명령어 치트시트

#### 워크트리 생성 (방 만들기)

메인 프로젝트 상위 폴더(`../`)에 새 폴더를 만들고, 새로운 브랜치를 파서 들어갑니다.

```bash
# 문법: git worktree add -b [새브랜치명] [새폴더경로] [기준브랜치]
$ git worktree add -b feature/login-ui ../my-project-ui main
```

#### 목록 확인 (방 현황 보기)

```bash
$ git worktree list
# 결과:
# /path/to/main      (main)
# /path/to/ui-work   (feature/login-ui)
```

#### 워크트리 삭제 (방 빼기)

작업이 끝난 워크트리 폴더는 그냥 지우지 말고 무조건 명령어로 삭제합니다.

```bash
$ git worktree remove ../my-project-ui
```

### 주의사항: "도플갱어 금지"

Git Worktree에는 딱 하나의 절대 규칙이 있습니다.

> **"하나의 브랜치를 두 곳의 워크트리에서 동시에 체크아웃할 수 없다."**

만약 메인 폴더가 `feature/login` 브랜치에 있는데, 워크트리에서 또 `feature/login`을 열려고 하면 Git이 충돌을 막기 위해 에러를 뿜습니다.

**해결책:**

그래서 본문에서 소개한 것처럼, 항상 **'파생 브랜치'**를 만들어야 합니다.

- 메인: `feature/login` (통합용)
- 워크트리1: `feature/login-ui` (작업용)
- 워크트리2: `feature/login-api` (작업용)
