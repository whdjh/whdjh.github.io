## 들어가며: 하나의 글이 관점을 바꿨다

최근 토스플레이스 기술 블로그에서 SDK 설계에 관한 글을 읽었다. 결제 단말기의 외부 연동 SDK를 "쓰기 쉽게" 만들기 위해 어떤 고민을 했는지에 대한 글이었는데, 읽고 나서 한동안 머릿속에 남았다.

단순히 SDK 이야기가 아니었다. 이 글이 던지는 질문의 본질은 이거였다.

> "좋은 인터페이스란, 사용자가 올바른 방법으로만 쓸 수 있도록 유도하는 것이 아닐까?"

주니어 개발자로서 그동안 "쓰기 쉬운 코드"라고 하면 네이밍이 직관적이고, 문서가 친절한 것 정도로만 생각했다. 하지만 이 글을 읽고 나서 생각이 달라졌다. 쓰기 쉽다는 것은 단순히 이해하기 쉽다는 게 아니라, **잘못 쓰기 어려운 구조**를 의미하는 것이었다.

---

## 1. 편리한 인터페이스 vs 안전한 인터페이스

코드를 작성하다 보면 "자유도가 높은 인터페이스"와 "제약이 있는 인터페이스"를 자주 마주친다.

처음에는 자유도가 높은 쪽이 무조건 좋은 거라고 생각했다. 내가 원하는 대로 제어할 수 있으니까. 하지만 경험이 쌓이면서 느낀 건, **자유도가 높을수록 실수할 여지도 비례해서 커진다**는 것이다.

토스플레이스 글에서 든 예시가 이걸 잘 보여준다. 서버를 열고 닫는 SDK에서 개발자가 직접 해야 하는 절차가 5단계였다.

1. 서버 열기
2. 연결 이벤트 등록
3. 메시지/에러 콜백 등록
4. 핸들러 제거
5. 서버 닫기

각 단계의 네이밍은 명확하고, 하나하나는 어렵지 않다. 그런데 4번을 빼먹으면? 메모리 누수가 발생한다. 3번을 연결 전에 등록하면? 동작하지 않는다.

즉, "쓰기 쉬운" 인터페이스였지만 "안전한" 인터페이스는 아니었던 것이다.

이 문제를 해결한 방식은 단순했다. **5단계를 2단계로 줄인 것이다.**

1. `start()`에 필요한 콜백을 넘기고
2. 끝나면 `stop()`을 호출한다

나머지는 SDK 내부가 알아서 처리한다. 이렇게 되면 개발자가 실수할 여지 자체가 줄어든다. 순서를 틀릴 수도 없고, 정리를 빼먹을 수도 없다.

---

## 2. 이케아 설명서로 이해하는 Facade 패턴

이 설계 방식을 **Facade 패턴**이라고 부른다. 보통 "복잡한 시스템을 단순한 인터페이스로 감싸는 패턴"으로 정의되지만, 나는 이렇게 이해했다.

> Facade 패턴은 "사용자의 의도"를 기준으로 인터페이스를 재구성하는 것이다.

이케아 가구로 비유하면 이렇다.

- **Facade 없는 설계** = 나사, 볼트, 판넬, 공구가 전부 따로 들어있고, 어떤 순서로 조립해야 하는지 내가 판단해야 하는 상태. 나사를 빼먹으면 가구가 흔들린다.
- **Facade가 적용된 설계** = 반조립된 모듈이 제공된다. "상판 끼우기 -> 다리 붙이기" 두 단계면 끝. 나사 빼먹을 일이 구조적으로 없다.

여기서 핵심은 반조립 모듈을 제공하는 이유가 "편하라고"가 아니라는 것이다. **나사를 빼먹는 실수를 원천적으로 방지하기 위해서다.** 편의성은 안전성의 부산물인 셈이다.

---

## 3. 80%의 편리함과 20%의 자유 — 둘 다 필요하다

하지만 Facade만 제공하면 되는 걸까? 그렇지 않다.

토스플레이스 글에서 인상 깊었던 부분은 **high-level과 low-level 인터페이스를 동시에 제공한다**는 점이었다. 이건 파레토 법칙(80/20 법칙)과 맞닿아 있다.

- **80%의 사용자**는 반복적인 공통 패턴으로 SDK를 쓴다 -> high-level(Facade)로 충분
- **20%의 사용자**는 특수한 요구사항이 있다 -> low-level API(탈출구)가 필요

AWS CDK도 같은 설계를 쓴다. L2(고수준)로 대부분의 리소스를 간편하게 만들 수 있지만, 세밀한 제어가 필요하면 L1(저수준)으로 내려갈 수 있다.

이 구조에서 배운 점은, **좋은 인터페이스는 "하나의 정답"을 강요하지 않는다**는 것이다. 대부분의 경우에는 안전하고 간편한 길을 제공하되, 필요할 때 내려갈 수 있는 탈출구를 열어두는 것. 이 균형이 인터페이스 설계의 핵심이라고 느꼈다.

---

## 4. SDK를 넘어서 — 인터페이스 설계의 보편적인 원칙들

이 글을 읽고 나서 돌아보니, 이미 좋은 인터페이스 설계를 적용한 사례들이 주변에 많았다.

React의 `useEffect` cleanup도 비슷한 사례다. cleanup 함수를 리턴하도록 설계해서, 이벤트 리스너 등록과 해제가 하나의 흐름 안에서 이루어진다. 만약 등록과 해제를 별도 함수로 각각 호출하게 했다면, 해제를 빼먹는 실수가 훨씬 많았을 것이다.

```js
useEffect(() => {
  window.addEventListener('resize', handleResize);

  return () => window.removeEventListener('resize', handleResize);
}, []);
```

React Hook Form도 그렇다. 폼의 상태 관리, 유효성 검사, 에러 핸들링을 하나하나 직접 구현하려면 복잡하지만, `register`와 `handleSubmit`이라는 high-level 인터페이스로 대부분의 유즈케이스를 커버한다. 그러면서도 `watch`, `setError`, `getValues` 같은 low-level API를 열어두어 세밀한 제어가 가능하다.

이런 사례들을 보면서 느낀 공통점을 정리하면 이렇다.

- **"잘못 쓰기 어려운" 구조를 먼저 고민한다** — 사용자가 실수할 수 있는 지점을 파악하고, 그 가능성을 구조적으로 줄인다
- **사용자의 "의도"를 기준으로 인터페이스를 나눈다** — 내부 구현의 단위가 아니라, 사용자가 하고 싶은 일의 단위로 API를 설계한다
- **편리함과 자유도의 균형을 잡는다** — 대부분에게는 안전한 고수준 인터페이스를, 특수한 경우에는 저수준 탈출구를 제공한다

---

## 마치며: 사용자의 실수는 설계의 실수다

주니어 개발자로서 이 글을 읽기 전에는 "개발자가 문서를 잘 읽고 올바르게 사용하는 게 당연한 거 아닌가?"라고 생각했다. 하지만 토스플레이스 글의 이 문장이 인상 깊었다.

> 연동사의 휴먼 에러가 SDK 플랫폼의 안정성과 별개의 일이 될 수는 없다.

결국 사용자가 실수하면, 그건 사용자의 문제가 아니라 **설계의 문제**라는 관점이다.

이건 SDK에만 해당하는 이야기가 아니다. 함수를 만들 때, 컴포넌트를 설계할 때, API를 정의할 때 — 항상 **"이걸 잘못 쓸 수 있는 방법이 있을까?"**를 먼저 고민해보는 습관이 좋은 인터페이스를 만드는 출발점이 아닐까.

아직 많이 부족하지만, 이 하나의 관점을 얻은 것만으로도 코드를 바라보는 눈이 조금 달라진 것 같다.
