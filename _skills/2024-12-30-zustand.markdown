2024년 12월 30일, 프로젝트에서 프로필 정보를 수정해도 새로고침하기 전에는 화면이 갱신되지 않는 문제가 있었다.

> **수정은 됐는데 화면만 안 바뀌어서 새로고침을 해야 했다.**  
> **전역 상태를 어떻게 관리하면 좋을까?**

상태와 UI가 제대로 연결되지 않아, 전역 상태 관리 라이브러리 도입을 검토하게 되었고 그 과정을 정리해 보았다.

---

## 문제 상황

프로필 정보를 수정했을 때, 새로고침을 해야만 UI가 갱신되는 문제가 있었다.
상태와 UI가 제대로 연결되어 있지 않아, 사용자 경험이 일관되지 않고 오류가 발생할 수 있었다.

---

## 과정

### 상태관리 종류

- **로컬 상태**: React에서는 useState로 관리
- **전역 상태**: zustand, recoil, redux, context API 등으로 관리
- **서버 상태**: React Query로 관리

### Zustand를 왜 선택했지?

- vanilla js 기준 공식 홈페이지의 20 line 정도의 예시를 읽어도 쉽게 이해 및 적용이 가능할 정도의 완만한 러닝커브를 가지고 있어 2달이내의 팀프로젝트 진행시 보일러플레이팅이 낮았음 → Redux는 보일러 플레이팅이 너무 컸음
- 아키텍처나 패턴을 강제하지 않는 매우 유연한 라이브러리
- ContextAPI와 다르게 불필요한 렌더링 최소화하여 성능저하를 줄인다.
- ContextAPI, Recoil과 다르게 provider 없는 구조
- recoil과 redux보다 더 작은 번들 사이즈

### Zustand를 활용한 전역 상태 관리

전역 상태를 정의하고, 필요한 컴포넌트에서 쉽게 접근할 수 있도록 store를 구성했다.

```tsx
interface UserState {
  user: UserResponse | null;
  setUser: (user: UserResponse) => void;
  clearUser: () => void;
}

export const useUserStore = create<UserState>((set) => ({
  user: null,
  setUser: (user) => set({ user }),
  clearUser: () => set({ user: null }),
}));
```

### 프로필 수정 시 상태 업데이트

서버에서 수정이 완료되면, setUser를 호출하여 전역 상태를 갱신했다.
컴포넌트는 전역 상태를 구독하고 있기 때문에 자동으로 UI가 업데이트되었다.

```tsx
const { user, setUser } = useUserStore();
await updateProfile.mutateAsync(data);
setUser({ ...user, username: data.username });
```

### 클라이언트와 서버 데이터 동기화

- 새로고침 없이도 최신 서버 데이터와 UI를 동기화할 수 있었다.
- Zustand의 persist 기능을 활용하여 새로고침 이후에도 상태 유지가 가능했다.

---

## 결과: 이제는 이렇게 정리할 수 있다

프로필 수정 후 즉시 UI가 갱신되어 사용자 경험이 향상되었다.
전역 상태 관리 덕분에 여러 컴포넌트에서 동일한 데이터를 일관되게 사용할 수 있게 되었다.
서버와 클라이언트 상태를 동기화하고, 유지보수가 용이한 구조를 설계할 수 있었다.

---

## 마치며

Zustand 도입으로 **상태와 UI가 한 방향으로 흐르는 구조**를 만들 수 있었다.

- 전역 상태를 store로 두고 구독만 하면 → 수정 시 UI가 자동으로 갱신된다.
- provider 없이 가볍게 쓰고, persist로 새로고침 후에도 유지할 수 있다.

앞으로도 전역 상태가 필요할 때는 “어디서 갱신하고, 어디서 구독할지”만 정해 두면 된다.
