## 왜 공부했는가

프로젝트를 진행하다 보면 변수·함수 사용 실수로 인한 런타임 에러가 자주 난다.  
특히 협업에서는 내가 쓰지 않은 코드·데이터를 다루다 보니 이런 오류가 더 자주 발생한다.  
개인 프로젝트에서는 실수가 적어 크게 문제되지 않지만, 규모가 큰 프로젝트에서는 업무 효율과 안정성에 직접 영향을 주기 때문에 예방 방법이 필요하다.

---

## 문제 상황

JavaScript만 사용하면, 대부분의 오류는 실행해 봐야 확인할 수 있다.

- 변수 타입 실수
- 함수 매개변수 전달 오류
- API 응답 데이터 구조와의 불일치

이런 문제는 실행 시점까지 발견되지 않으면, 버그 수정 시간이 늘고 서비스 안정성이 떨어진다.  
특히 팀 단위로 진행할 때, 다른 사람이 작성한 코드와 연동하는 과정에서 실수로 인한 버그가 잘 발생한다.

---

## 공부 내용

TypeScript는 JavaScript에 타입 시스템을 더한 언어로, 다음과 같은 장점이 있다.

- 런타임 에러 사전 방지: 타입 검사·컴파일 단계에서 오류를 미리 잡을 수 있다.
- API 인터페이스 정의: 백엔드·프론트엔드 간 데이터 구조를 명확히 정의하고, 타입 불일치로 인한 오류를 줄일 수 있다.
- 협업 시 안정성: 코드 작성 시 타입 정보를 참고할 수 있어, 다른 팀원 코드와의 호환성을 높일 수 있다.

---

### Type vs Interface

#### Type

- 복잡한 타입 조합에 적합하다.
- 유니온(`|`), 인터섹션(`&`) 등으로 새 타입을 만들 수 있다.
- 여러 타입을 조합하거나 리터럴 타입을 정의할 때 유용하다.

```tsx
type ID = string | number;
type User = { name: string } & { age: number };
```

#### Interface

- 객체 구조 정의에 맞춰져 있다.
- 선언 병합(Declaration Merging)을 지원해, 같은 이름의 인터페이스를 여러 번 선언하면 자동으로 합쳐진다.
- 객체 타입을 확장할 때 우선 고려한다.

```tsx
interface User {
  name: string;
}

interface User {
  age: number;
}
```

---

### Type/Interface를 쓰면 얻는 이점

1. 재사용성: 같은 구조를 여러 곳에서 쓸 때 한 번만 정의하면 된다. 명시적 타입만 쓰면 매번 같은 구조를 반복해야 한다.
2. 유지보수성: 구조가 바뀌면 Type/Interface는 한 곳만 수정하면 되고, 명시적만 쓰면 쓰는 모든 곳을 찾아 수정해야 한다.
3. 가독성: `User` 같은 이름만 봐도 어떤 데이터인지 파악하기 쉽다. 명시적만 쓰면 긴 타입 정의를 매번 읽어야 한다.
4. 문서화: Type/Interface에 JSDoc을 달면, 해당 타입을 쓰는 곳에서 자동으로 문서를 볼 수 있다.
5. 타입 확장·조합: 복잡한 타입을 만들 때 기존 타입을 확장하거나 조합하기 좋다.

### 생기는 단점

1. 추가 코드: 간단하거나 한 번만 쓰는 타입까지 모두 선언하면 코드가 길어질 수 있다.
2. 과도한 추상화: Type/Interface를 너무 많이 만들면, 정의를 찾아가며 읽어야 해서 오히려 파악이 어려워질 수 있다.

## 그래서 언제 뭘 써야 할까?

### Type/Interface로 선언하는 게 좋은 경우

- API 응답 데이터 구조
- 여러 곳에서 재사용되는 객체 타입
- Props, State 같은 컴포넌트 관련 타입
- 비즈니스 로직에서 중요한 도메인 모델

### 명시적으로만 써도 되는 경우

- 함수 내부의 간단한 로컬 변수
- 한 번만 쓰는 단순한 매개변수
- 프리미티브 타입 (string, number, boolean)
