## 409가 무슨 에러인가요?

최근 면접에서 HTTP 상태 코드에 대한 질문을 받았다. 평소 실무에서 에러를 처리하면서 나름 안다고 생각했는데, 막상 409 Conflict에 대해 설명하면서 "사용자 안내를 위한 커스텀 에러"라고 답했다.

틀린 답이었다. 409는 HTTP 표준에 정의된 공식 상태 코드다. 백엔드가 임의로 만든 게 아니라, "리소스의 현재 상태와 요청이 충돌한다"는 의미를 표현하기 위해 스펙에서 정해둔 코드였다.

돌아와서 생각해보니, 400과 422의 차이도 모호했고, 401과 403을 어떻게 구분해서 처리해야 하는지도 명확하지 않았다. 이참에 프론트엔드 개발자 관점에서 실무에 꼭 필요한 에러 코드들을 제대로 정리해보기로 했다.

---

## 4xx — 클라이언트 에러

4xx대 에러는 "요청을 보낸 쪽에 문제가 있다"는 의미다. 즉, 프론트엔드 개발자가 직접 원인을 파악하고 해결해야 할 가능성이 높은 에러들이다.

### 400 Bad Request

서버가 요청을 이해할 수 없을 때 발생한다. 대부분 프론트에서 보낸 데이터의 형식이 잘못된 경우다. 날짜 필드에 "어제"라는 문자열을 보내거나, 숫자 필드에 일반 문자열을 보내는 것이 대표적인 예다.

API 스펙에서 요구하는 타입과 포맷을 정확히 맞춰야 하며, 폼 유효성 검사(validation)를 프론트 단에서 철저히 수행하는 것이 최선의 예방책이다.

### 401 Unauthorized

한 마디로 "너 누구야?"다. 인증이 안 된 상태, 즉 토큰이 없거나 만료됐을 때 발생한다.

프론트에서는 401을 받으면 토큰 갱신(refresh)을 시도하고, 그마저 실패하면 로그인 페이지로 리다이렉트하는 흐름을 구현해야 한다. 이 에러를 제대로 처리하려면 바로 다음에 나오는 403과의 차이를 반드시 알아야 한다.

### 403 Forbidden

"너인 건 알겠는데, 거기는 못 가." 인증은 됐지만 해당 리소스에 접근할 권한이 없는 경우다. 일반 사용자가 관리자 전용 API를 호출하는 것이 대표적인 예다.

401과의 핵심 차이는 이렇다.

- 401: 로그인 자체가 안 됨 → 로그인 페이지로 이동
- 403: 로그인은 됐지만 권한 부족 → "권한이 없습니다" 안내

면접에서도 자주 나오는 질문인데, 가장 중요한 포인트는 403이 왔을 때 절대 로그아웃을 시키면 안 된다는 것이다. 사용자는 정상적으로 로그인한 상태이기 때문이다. 권한이 없는 메뉴나 버튼은 아예 숨기거나 비활성화해서 403 자체가 발생하지 않도록 설계하는 것이 가장 좋다.

### 404 Not Found

요청한 리소스가 존재하지 않을 때 발생한다. URL 오타, 이미 삭제된 게시글 조회 등이 흔한 원인이다.

404 전용 페이지를 반드시 만들어두고, 삭제된 항목에 접근했을 때는 목록 페이지로 자연스럽게 안내하는 처리가 필요하다. 개발 중이라면 엔드포인트 URL을 다시 한 번 확인해보는 것도 잊지 말자.

### 405 Method Not Allowed

GET만 허용된 엔드포인트에 POST를 보내는 것처럼 HTTP 메서드가 잘못된 경우다. 실무에서는 API 문서를 잘못 읽었거나, 복사/붙여넣기 실수로 발생하는 경우가 많다. API 문서를 다시 확인하면 대부분 바로 해결된다.

### 409 Conflict

서두에서 말했던 그 에러다. 리소스의 현재 상태와 요청이 충돌할 때 발생하는 HTTP 표준 에러 코드다.

이미 존재하는 이메일로 회원가입을 시도하거나, 두 명이 동시에 같은 문서를 편집해서 버전이 충돌하는 것이 대표적인 예다. 다른 4xx 에러와 다른 점은, 상황마다 사용자에게 보여줘야 할 안내 메시지가 달라진다는 것이다.

- 이메일 중복 → "이미 사용 중인 이메일입니다"
- 버전 충돌 → "다른 사용자가 수정했습니다. 새로고침 해주세요"
- 상태 충돌 → "이미 취소된 주문입니다"

그래서 실무에서는 백엔드가 응답 body에 세부 에러 코드나 메시지를 함께 내려주고, 프론트가 그걸 기반으로 분기 처리하는 패턴이 일반적이다. 내가 "커스텀 에러"라고 착각했던 이유도, 이런 백엔드와의 협의 과정에서 커스텀 처리가 많이 들어가기 때문이었던 것 같다.

### 413 Payload Too Large

파일 업로드 시 서버가 허용하는 크기를 초과했을 때 발생한다. 서버에서 거부당한 뒤 에러를 보여주는 것보다, 업로드 전에 프론트에서 파일 크기를 미리 체크하는 것이 훨씬 좋은 사용자 경험이다. "최대 10MB까지 업로드 가능합니다" 같은 안내를 파일 선택 시점에 보여주자.

### 422 Unprocessable Entity

요청의 형식(syntax)은 맞지만, 의미(semantic)적으로 처리할 수 없는 경우다.

400과 비슷해 보이지만 차이가 있다. 400은 "JSON 파싱 자체가 안 된다" 수준이고, 422는 "JSON은 잘 읽히는데 나이가 -5살이라 처리가 안 된다" 수준이다. 백엔드와 협의해서 400과 422를 구분해서 사용하면, 프론트에서 에러 유형에 따라 더 정확한 안내 메시지를 보여줄 수 있다.

### 429 Too Many Requests

짧은 시간 안에 요청을 너무 많이 보냈을 때 발생한다. 버튼 연타, 무한 루프에 빠진 API 호출 등이 원인이다.

대응은 두 가지다. 첫째, 예방 차원에서 디바운스(debounce)와 쓰로틀링(throttling)을 적용한다. 둘째, 429를 받았을 때는 응답의 `Retry-After` 헤더를 확인해서 해당 시간 이후에 재시도하는 로직을 구현한다.

## 5xx — 서버 에러

5xx대 에러는 "서버 쪽에 문제가 있다"는 의미다. 프론트 코드의 잘못은 아니지만, 사용자에게 적절한 안내를 하는 것은 프론트의 몫이다.

### 500 Internal Server Error

서버 내부에서 예상치 못한 에러가 발생한 경우다. 가장 포괄적인 서버 에러로, 구체적인 원인은 백엔드 로그를 확인해야 한다.

프론트에서는 "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요"와 같은 사용자 친화적인 메시지를 보여주는 것이 핵심이다. 기술적인 에러 메시지를 그대로 노출하면 사용자는 혼란만 느끼게 된다.

### 502 Bad Gateway

서버 앞단의 프록시나 로드밸런서가 백엔드 서버로부터 비정상적인 응답을 받았을 때 발생한다. 배포 진행 중이거나 서버 프로세스가 죽었을 때 자주 볼 수 있다.

프론트 개발자 입장에서 502는 "서버가 지금 불안정한 상태"라고 이해하면 된다. 잠시 후 재시도하거나, 백엔드/인프라 팀에 상황을 공유하면 된다.

### 503 Service Unavailable

서버가 점검 중이거나 과부하 상태일 때 발생한다. 미리 서비스 점검 안내 페이지를 준비해두는 것이 좋다. 계획된 점검이라면 백엔드에서 점검 시간 정보를 함께 내려줄 수 있으므로, 이를 활용해 "00시 00분까지 점검 중입니다"처럼 구체적인 안내를 보여주면 사용자 경험이 훨씬 좋아진다.

### 504 Gateway Timeout

서버의 응답 시간이 제한을 초과했을 때 발생한다. 대량 데이터 조회나 엑스포트 같은 무거운 작업에서 흔히 발생한다.

프론트에서는 긴 작업에 대해 로딩 인디케이터를 보여주고, 타임아웃 발생 시 "처리에 시간이 걸리고 있습니다"라는 안내와 함께 재시도 버튼을 제공하는 것이 좋다. 근본적으로는 백엔드와 협의해서 무거운 작업을 비동기 처리로 전환하는 것이 해결책이다.

## 마무리

면접에서 409를 커스텀 에러라고 답했던 게 이 글을 쓰게 된 계기였다. 정리하고 보니 에러 코드를 "아는 것"과 "정확히 아는 것" 사이에는 꽤 큰 차이가 있었다.

프론트엔드 개발자에게 에러 처리란 결국 사용자 경험의 문제다. 핵심은 세 가지로 요약할 수 있다.

- 401과 403은 반드시 구분한다. 인증 실패와 권한 부족은 완전히 다른 상황이다.
- 4xx는 예방하고, 5xx는 안내한다. 클라이언트 에러는 validation으로 막고, 서버 에러는 사용자 친화적 메시지로 대응한다.
- 에러 메시지는 사용자의 언어로 쓴다. "422 Unprocessable Entity"가 아니라 "입력한 값을 확인해주세요"가 정답이다.

다음에 면접에서 같은 질문을 받는다면, 이번에는 제대로 답할 수 있을 것 같다.
