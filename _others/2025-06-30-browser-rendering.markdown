## 왜 공부하게 되었나?

매일 크롬, 사파리, 엣지 같은 브라우저를 사용하면서 HTML, CSS, JavaScript를 작성하지만, "브라우저가 어떻게 내 코드를 화면에 그려내는가?"에 대해서는 깊이 생각해본 적이 없었다.

특히 성능 최적화를 하면서 자주 듣게 되는 말들이 있었다.

- "DOM 조작은 비싸다"
- "CSS는 위에서부터 파싱된다"
- "브라우저는 싱글 스레드로 동작한다"

하지만 이런 말들의 진짜 의미를 정확히 이해하지 못했다. 단순히 "그렇다더라" 수준으로는 근본적인 성능 문제를 해결할 수 없다는 것을 깨달았다.

또한 웹 개발을 하면서 자주 마주치는 상황에 대한 궁금증이 있었다.

- 주소창에 URL을 입력하고 엔터를 누르는 순간부터 화면에 페이지가 나타나기까지 정확히 무슨 일이 일어나는가?
- HTML 파일 하나가 어떻게 우리가 보는 웹페이지로 변환되는가?
- CSS와 JavaScript는 언제, 어떤 순서로 처리되는가?

이런 근본적인 질문에 답하려면 브라우저의 내부 동작 원리를 알아야 한다고 생각했고, 더 나은 개발자가 되기 위한 필수 과정이라고 판단했다.

---

## 문제 상황

랜딩 페이지 성능 개선 작업을 맡게 되면서 시작되었다. 사용자들이 "페이지 로딩이 너무 느리다"는 피드백을 보내왔고, 팀에서는 이탈률 개선을 위해 로딩 속도 최적화를 기획했다.

Chrome DevTools의 Network 탭을 확인해보니 여러 문제가 보였다.

- Largest Contentful Paint (LCP)
- Cumulative Layout Shift (CLS)

![LCP, CLS 등 성능 지표](/assets/img/9.png)

하지만 "왜 이런 현상이 발생하는가?"에 대해서는 명확하게 설명할 수 없었다. 동료들과 논의해봐도:

- "CSS는 head에 넣어야 한다더라"
- "JavaScript는 body 맨 아래 넣으면 된다더라"
- "이미지는 lazy loading을 써야 한다더라"

정도의 경험적 지식만 있을 뿐, 근본적인 원리는 모르는 상태였다.

특히 당황스러운 것은 같은 HTML 파일인데도 브라우저마다 로딩 패턴이 다르다는 점이었다. Chrome에서는 빨랐던 페이지가 일부 모바일 브라우저에서는 훨씬 느렸다. 이런 차이가 왜 발생하는지, 어떻게 해결해야 하는지 갈피를 잡을 수 없었다.

이때 깨달았다. 표면적인 최적화 기법만 알아서는 한계가 있다는 것. 브라우저가 HTML을 받아서 화면에 그려내는 전체 과정을 이해해야만 진짜 최적화를 할 수 있다는 것이다.

## 공부한 내용

### 1. 브라우저란?

- 다양한 웹사이트를 방문하고 웹 페이지를 표시하는 역할을 한다.
- 사용자가 주소를 입력하거나 링크를 클릭하면, 브라우저는 해당 웹페이지의 내용을 가져와 화면에 표시한다.
- 예: Chrome, Edge, Safari 등

### 3. 렌더링 과정

#### 3-1. URL 입력부터 시작

`www.naver.com`을 검색한다고 하자.

![URL 입력 후 흐름](/assets/img/11.png)

#### 3-2. DNS 조회

- 브라우저는 먼저 도메인 이름을 IP 주소로 변환한다.
- 캐시된 DNS 기록을 먼저 확인하고, 없으면 DNS 서버에 요청해 해당 IP 주소를 얻는다.
- 예: `www.naver.com`이 CNAME으로 `www.naver.com.nheos.com`으로 리다이렉트되는 경우

![DNS CNAME 리다이렉트](/assets/img/12.png)

#### 3-3. TCP 연결 (3-way handshake)

IP 주소를 확인한 뒤, 브라우저는 서버와 TCP 연결을 수립한다. 3-way handshake를 수행한다.

![TCP 3-way handshake](/assets/img/13.png)

1. 클라이언트 → 서버: 접속 요청 SYN 패킷 전송
2. 서버 → 클라이언트: 수락하며 SYN + ACK 패킷 응답
3. 클라이언트 → 서버: ACK 패킷 전송으로 연결 확정
4. 이제 TCP 레벨에서 데이터 전송이 가능한 상태가 된다.

#### 3-4. TLS Handshake (보안 채널 설정)

TCP 연결 위에서 TLS가 동작하며, 암호화 통신을 위한 협상이 이루어진다.

- Client Hello: 브라우저가 지원하는 TLS 버전, 암호화 알고리즘 목록, 세션 ID, Client Random 등을 서버에 전송
- Server Hello + Certificate: 서버가 선택한 암호화 알고리즘, Server Random, 서버 인증서(공개키 + CA 서명) 전송
- 인증서 검증: 브라우저가 CA 체인으로 인증서를 검증하고 서버 신원 확인
- Pre-Master Secret 교환: 브라우저가 서버 공개키로 Pre-Master Secret을 암호화해 전송 → 서버가 개인키로 복호화
- 대칭키 생성: Client Random, Server Random, Pre-Master Secret을 조합해 양측이 동일한 대칭키 생성
- Finished 메시지 교환: 생성된 대칭키로 암호화된 Finished 메시지를 주고받으며 암호화가 올바른지 검증

이후에는 이 대칭키로 HTTP 요청/응답을 암호화해 주고받는다.

#### 3-5. HTTP 요청/응답

- 서버가 요청을 받고 해당 리소스를 브라우저에 HTTP 응답 코드와 함께 전달한다.
- HTML 파일을 응답으로 받는다.

```html
<html>
  <head>
    <style>
      h1 {
        color: red;
      }
    </style>
  </head>
  <body>
    <h1>1번 문장</h1>
    <h2>2번 문장</h2>
  </body>
</html>
```

#### 3-6. HTML 파싱 → DOM 트리

브라우저는 이 텍스트 파일을 파싱하면서 노드로 표현된 DOM 트리를 생성한다.

```
Document
└── html
    ├── head
    │   └── style
    └── body
        ├── h1
        │   └── "1번 문장"
        └── h2
            └── "2번 문장"
```

#### 3-7. CSS 파싱 → CSSOM 트리

HTML 내의 CSS를 파싱해 CSSOM 트리가 생성된다.

```
StyleSheet
└── Rule
    └── Selector: h1
        └── Declaration
            └── property: color
                value: red
```

#### 3-8. 렌더 트리

완성된 DOM + CSSOM을 이용해 화면에 보여질 요소만 추려 렌더 트리를 만든다.

```
RenderTreeRoot
├── h1 (color: red)
│   └── "1번 문장"
└── h2 (default style)
    └── "2번 문장"
```

#### 3-9. 레이아웃 & 페인트

- 렌더 트리 노드의 정확한 위치와 크기를 계산한다. (레이아웃)
- 계산된 위치와 크기를 기반으로 화면에 그린다. (페인트)

## 깨달은 점

브라우저 렌더링 과정을 제대로 공부한 후, 웹 개발에 대한 관점이 달라졌다.

### 전체적인 웹 동작 원리 이해

- 사용자가 주소창에 URL을 입력하는 순간부터 화면에 페이지가 표시되기까지의 전체 과정을 단계별로 설명할 수 있게 되었다.
- DNS 조회, TCP 연결, HTTP 요청/응답, HTML 파싱, DOM 트리 생성까지의 흐름이 머릿속에 그려진다.

### HTML/CSS/JavaScript의 처리 순서 이해

- 왜 CSS를 head에 넣어야 하는지, JavaScript의 위치가 왜 중요한지 이제 설명할 수 있다.
- HTML 파싱이 어떻게 진행되고, 언제 CSSOM 트리가 만들어지며, 렌더 트리는 언제 구성되는지 이해하게 되었다.

### 근본적인 성능 최적화 능력 향상

이전의 성능 최적화 작업을 다시 돌아보니 다른 접근이 가능해졌다.

- CSS 파일이 순차 로드될 때마다 CSSOM 재구성으로 렌더링이 블로킹된다.
- `head`의 JavaScript가 HTML 파싱을 중단시켜 DOM 트리 생성이 지연된다.
- 큰 이미지가 Initial Paint 시점을 늦춘다.

이제 "왜 그런지"를 알고 대응할 수 있게 되었다.
