## 도커(Docker)란?

**공식 정의:** 애플리케이션의 모든 코드 및 종속성을 표준 형식으로 패키징하여, 컴퓨팅 환경 전반에서 빠르고 안정적으로 실행될 수 있게 해주는 소프트웨어 플랫폼이다.

**쉬운 이해:** "내 컴퓨터에선 되는데 왜 배포 서버(또는 쟤 컴퓨터)에선 안 되지?" 할 때 생기는 의존성(Dependency)과 환경 세팅 스트레스를 완전히 날려주는 구원자다. 내 코드와 실행 환경을 컨테이너라는 박스에 포장해서 어디서든 똑같이 돌아가게 만들어 준다.

## 도커 핵심 용어 4대장

### 도커 이미지 (Docker Image) = 🐟 붕어빵 틀 / Class

* **공식 정의:** 컨테이너로 실행될 소프트웨어 모음이다. 컨테이너 생성 지침이 포함되어 있으며, 한 번 생성되면 변경할 수 없다 (Read-only).
* **쉬운 이해:** React 코드 + Node.js 환경 + 의존성 패키지들을 꽝꽝 얼려놓은 '원본 템플릿'이다. 프론트엔드에서 컴포넌트나 클래스(Class)를 만들어 놓은 상태와 똑같다.

### 도커 컨테이너 (Docker Container) = 🍞 구워진 붕어빵 / Instance

* **공식 정의:** 하드웨어 가상화를 제공하는 VM과 달리 '사용자 공간'을 추상화하여 경량의 운영체제 수준 가상화를 제공하는, 실행 중인 도커 이미지 인스턴스다.
* **쉬운 이해:** 도커 이미지를 바탕으로 실제로 쌩쌩 실행 중인 상태다. 클래스를 `new` 키워드로 생성해서 메모리에 올린 인스턴스(Instance)라고 보면 된다. 하나의 이미지(틀)로 여러 개의 컨테이너(붕어빵)를 찍어낼 수 있다.

### 도커 엔진

* **공식 정의:** 컨테이너를 구축 및 실행하는 오픈 소스 호스트 소프트웨어 (클라이언트 서버 애플리케이션)다.
* **쉬운 이해:** 만들어진 이미지를 읽어서 내 컴퓨터에서 컨테이너로 실행시켜 주는 핵심 실행 프로그램이다.

### 도커 레지스트리

* **공식 정의:** 이미지를 저장 및 다운로드할 수 있는 무상태성을 갖춘 확장 가능한 서버측 애플리케이션이다.
* **쉬운 이해:** 남들이 만들어둔 도커 이미지를 다운받거나, 내 이미지를 올려서 공유하는 저장소다. 프론트엔드 개발자들이 매일 쓰는 npm 저장소나 GitHub (ex. Docker Hub)이라고 생각하면 된다.

## 도커는 왜 가볍고 빠를까? (가상머신 VM과의 결정적 차이)

도커를 공부하다 보면 "가상머신(VM)보다 훨씬 가볍고 빠르다"는 말을 자주 듣게 된다. 겉보기엔 둘 다 내 컴퓨터 안에 남의 환경을 띄우는 것 같은데 왜 그럴까?

**1. 집 짓기로 보는 근본적인 차이 (커널 공유)**
컴퓨터에는 하드웨어(CPU, 램)와 프로그램 사이를 연결해 주는 진짜 심장부, '커널(Kernel)'이라는 게 있다.

* **가상머신(VM) : 집 안에 '새 집' 통째로 짓기**
내 맥북(Host OS) 위에 가상의 하드웨어를 흉내 내고, 그 위에 윈도우 같은 무거운 운영체제(Guest OS)와 새로운 커널을 통째로 새로 설치하는 방식이다.
무거운 OS를 처음부터 끝까지 부팅해야 하니 켜는 데 한참 걸리고 덩치도 크다.
* **도커(Docker) : 큰 집 안에 '칸막이'만 치기**
도커는 컨테이너 안에 윈도우나 리눅스 같은 무거운 운영체제(Guest OS)를 아예 깔지 않는다.
대신 내 맥북의 심장부인 '커널'을 그대로 빌려 쓰면서(공유하면서), 프로그램들이 서로 침범하지 못하게 완벽한 칸막이(격리, Isolation)만 쳐주는 방식이다.
OS를 부팅할 필요가 없으니 1초 만에 즉시 실행된다.

**2. 내 램(RAM)이 8기가라면? (메모리 할당 방식의 차이)**
단순히 "둘 다 내 램을 갉아먹는 거 아니야?"라고 생각할 수 있지만, 자원을 가져가는 방식이 완전히 다르다.

* **가상머신(VM) = "방 미리 빼놓기"**
VM에 4기가를 할당하면, 그 안의 프로그램이 놀고 있어도 내 맥북 입장에선 4기가를 꼼짝없이 뺏긴 상태가 된다.
게다가 그 4기가 안에는 무거운 윈도우 OS가 켜져 있어야 해서, 실제 앱이 쓰지도 않는데 '숨만 쉬어도 나가는 유지비(OS 구동 램)'로 엄청난 공간을 낭비한다.
* **도커(Docker) = "딱 쓴 만큼만 내기"**
도커는 램을 무식하게 미리 뺏어가지 않는다. 띄워놓은 리액트 앱이 200MB만 필요하다면, 전체 8기가 중 유동적으로 딱 200MB만 사용한다.
무거운 Guest OS가 없기 때문에 쓸데없는 램 유지비가 0원에 가깝다. 남는 램으로 수십 개의 컨테이너를 더 띄울 수 있다.

**3. 극단적으로 둘 다 똑같이 램 4기가를 쓴다면 성능이 똑같을까?**
결론부터 말하면 "아니! 그래도 도커가 압도적으로 빠르다."
단순 램 용량 문제가 아니라, CPU가 일하는 연산 속도와 구조에서 근본적인 차이가 나기 때문이다.

* **통역사(Hypervisor)의 유무:** VM은 앱이 CPU에 명령을 내릴 때 `게스트 OS -> 하이퍼바이저(통역사) -> 호스트 OS -> 하드웨어`라는 복잡한 단계를 거쳐야 해서 연산 속도가 떨어진다. 반면 도커는 통역사가 아예 없이 다이렉트로 소통해서 네이티브(Native)에 가까운 빠른 속도가 나온다.
* **쓸데없는 백그라운드 노동:** VM 안의 OS는 시스템 업데이트, 네트워크 체크 등 잡다한 백그라운드 노동을 하느라 CPU를 갉아먹는다. 반면 도커는 무거운 OS가 없으므로 잡다한 노동 없이, 오롯이 '내가 띄운 앱' 하나에만 100%의 CPU 파워를 쾌적하게 몰아줄 수 있다.

## 도커가 바꾸는 실무 개발의 패러다임 (환경 변수와 MSA)

도커가 가볍고 빠르다는 것은 알겠다. 그렇다면 이 도커가 프론트엔드와 백엔드의 실제 업무 방식을 어떻게 바꿔놓았을까? 실무에서 도커를 활용하는 핵심 원리를 알아보자.

### 단 하나의 이미지로 모든 환경 제패하기 (환경 변수)

프론트엔드 개발 시 로컬 컴퓨터에서 사용하는 API 주소(`http://localhost:8080`)와 실제 고객이 사용하는 실서버 API 주소(`https://api.회사.com`)는 다르다. 그렇다면 개발용 도커 이미지 따로, 실서버용 도커 이미지 따로 두 번을 만들어야 할까? 정답은 "아니다"이다.

* **도커 이미지는 불변(Read-only)이다:** 도커 이미지는 한 번 구워내면 코드를 수정할 수 없는 '틀'이다. 테스트 환경이든 실서버 환경이든 무조건 똑같은 단 1개의 이미지를 사용한다.
* **환경 변수(.env) 주입:** 대신, 그 이미지로 컨테이너를 실행(Run)할 때 "이번에는 실서버 API 주소를 적용해라!"라고 실행 시점에 **환경 변수**를 밖에서 주입해 준다.

이를 통해 "내 로컬에선 됐는데 실서버에선 왜 안 되지?"라는 변수를 완벽하게 차단하고, 100% 동일한 환경으로 안전하게 배포할 수 있다.

### 아키텍처의 진화: 거대한 덩어리에서 레고 블록으로
서비스 규모가 커지면서 백엔드 아키텍처는 도커의 발전과 함께 크게 3단계로 진화해 왔다.

#### 모놀리식 (Monolithic)
과거에는 유저, 결제, 게시판 기능을 하나의 거대한 서버 덩어리로 묶어 단일 데이터베이스(DB)와 연결했다. 이 구조는 결제 쪽에 버그가 나서 서버가 다운되면 웹사이트 전체가 마비되는 치명적인 단점이 있었다.
![](/assets/img/112.png)

#### SOA (Service-Oriented Architecture)
모놀리식의 단점을 극복하고자 기능별로 서비스를 쪼개기 시작했다. 하지만 쪼개진 서비스들이 서로 통신하려면 무거운 '중앙 통제 버스(ESB)'를 무조건 거쳐야 했고, DB도 거대한 하나를 다 같이 공유하는 경우가 많아 완벽한 독립을 이루지 못했다.
![](/assets/img/113.png)

#### MSA (Micro Service Architecture)
이제는 도메인별로 백엔드 서버를 완전히 독립시킨다. 결제 서버, 유저 서버가 각자만의 도커 컨테이너 방을 갖고, 심지어 DB도 각자 따로 가진 채 가벼운 API로만 소통한다.
결제 서버가 죽어도 프론트엔드나 유저 서버는 살아있으므로 웹사이트는 정상 작동한다. 이 수십 개의 독립된 서버들을 환경 세팅 스트레스 없이 1초 만에 껐다 켰다 할 수 있게 완벽히 격리해 주는 기반 기술이 바로 도커(Docker)다.
![](/assets/img/114.png)

### 프론트엔드의 평화를 지켜주는 'API Gateway'

백엔드 서버가 도메인별로 10개로 쪼개졌다면, 프론트엔드 개발자는 10개의 베이스 URL을 전부 외우고 관리해야 할까? 다행히도 프론트엔드는 서버가 몇 개인지 알 필요가 전혀 없다. 중간에 **'API Gateway(안내데스크)'**가 존재하기 때문이다.

* **단일 베이스 URL 사용:** 프론트엔드는 모놀리식 시절처럼 단 1개의 베이스 URL(`https://api.회사.com`)로만 `fetch`나 `axios` 요청을 보낸다.
* **API Gateway의 알아서 매핑(Routing):** 요청을 받은 API Gateway가 주소의 뒷부분(Path)을 분석한다.
* `/users`로 오면 "유저 전용 도커 컨테이너로 가라!"
* `/payments`로 오면 "결제 전용 도커 컨테이너로 가라!"

결론적으로 프론트엔드는 백엔드 서버가 도커로 띄워졌는지, 몇 개로 쪼개졌는지 그 존재 자체를 몰라도 된다. 프론트는 화면 개발에만 집중하고, 백엔드는 기능별로 컨테이너를 관리하는 완벽한 **관심사의 분리(Decoupling)**가 이루어지는 것이다.
