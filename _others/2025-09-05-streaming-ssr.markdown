## 왜 공부하게 되었나?

기존 **SSR**은 **“모든 데이터가 준비될 때까지 페이지가 비어 있는 시간”**이 생겨, 초기 체감 속도와 탐색 가능성이 떨어졌다.  
**React/Next의 Streaming**은 준비된 UI를 **“조각”** 단위로 흘려보내서, 사용자에게 **더 빨리** 보여줄 수 있다.

## 공부 내용

### 원리

**loading.tsx**(페이지 단위) 또는 서버 컴포넌트의 **`<Suspense>`** 경계로 구역을 나누고, 서버가 **준비된 부분부터** HTML 청크를 **순차 전송**한다.  
그래서 **초기 골격·빠른 섹션**은 먼저 보이고, **느린 섹션**은 뒤에서 스트리밍으로 합류한다.

### 장점

- **FCP 단축**: 먼저 보여줄 수 있어 **체감 성능**이 올라감.
- **인터럽터블 네비게이션**: 로딩 중에도 **라우팅** 가능 → UX 향상.
- **느린 fetch가 전체를 블로킹하지 않음**(병렬·비차단) → 긴 경로의 **TTFB 의존도**를 낮춤.

### 측정 조건

- **Chrome DevTools Lighthouse** / Mode: Navigation / Device: Desktop
- **Categories**: Performance only
- 각 시나리오 **5회 측정** → **중앙값** / 매 회 하드 리로드

### 기존 SSR 성능

- **FCP**: 0.8s로 일관되게 빠름. 서버 렌더된 초기 뼈대가 곧바로 보였다는 뜻.
- **LCP**: 중앙값 1.9s(양호). 첫 시행에서 13.6s가 한 번 튐 → 콜드 스타트/자원 캐시 영향 가능성.
- **TBT**: 중앙값 1.85s. 메인 스레드가 꽤 막힌 편. SSR 자체보다 **클라이언트 JS·하이드레이션** 비용 영향.
- **Speed Index**: 2.5s, **CLS**: 0. 시각적 안정성과 페인트 진행 속도는 준수.

### Streaming SSR 성능

- **FCP**: 0.2s로 매우 빠름. 준비된 청크를 먼저 전송해 초기 가시 콘텐츠가 즉시 보임.
- **LCP**: 중앙값 0.4s(매우 우수). 한 번 2.3s로 튄 사례 있으나 스파이크 폭이 SSR 대비 크게 축소.
- **TBT**: 중앙값 420ms. 메인 스레드 정체가 크게 감소(SSR 1.85s → 0.42s). 하이드레이션/클라이언트 JS가 **경계 뒤로 분산**된 효과.
- **Speed Index**: 0.2s, **CLS**: 0. 화면 완성 속도가 매우 빠르고 시각적 안정성 유지.

### 비교 요약

| 지표 | 변화 |
|------|------|
| Performance | +9p |
| FCP | −0.6s (−75%) |
| LCP | −1.5s (−79%) |
| TBT | −1430ms (−77%) |
| Speed Index | −2.3s (−92%) |
| CLS | 동일(0) |

### 해석

FCP, Speed Index, LCP, TBT가 모두 개선됐고, 특히 **LCP −79%**, **TBT −77%**로 **체감 완성 시점**과 **상호작용 대기**가 줄었다.  
SSR에서 한 번 튄 **LCP 13.6s** 스파이크도 Streaming에서는 **2.3s** 수준으로 완화됐다.
