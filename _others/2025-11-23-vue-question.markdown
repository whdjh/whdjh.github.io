## "Vue 배워야 할까요?"

입사 후 팀에서 **Vue**를 쓰는 걸 보고, 리드 개발자와 **커피챗** 자리에서 물었다.

**"Vue를 공부해야 할까요?"**

돌아온 답은 예상과 달랐다.

**"왜 그 라이브러리를 써야 하는지 먼저 고민해봐요. React는 왜 써요?"**

나는 자신 있게 대답했다.

**"컴포넌트화 때문 아닌가요?"**

리드가 되물었다.

**"Vue도 컴포넌트화 되는데?"**

**"...그러네요?"**

순간 머리가 하얘졌다. **React를 쓰는 이유**를 제대로 말하지 못했다.  
그냥 React가 인기 많고, 회사에서 많이 쓰고, 자료가 많아서 정도였다.  
**도구를 선택하는 기준**이 없다는 걸 그제야 깨달았다.

---

## 그럼 React는 왜 썼을까?

다시 생각해 봤다. 내가 **React**를 선택한 이유는 뭐였을까?

- **생태계**가 넓었다. 라이브러리도 많고, 커뮤니티도 크고, 해결책을 찾기 쉬웠다.
- **TypeScript**와 잘 맞았다. JSX에서 타입을 명확히 정의할 수 있고, props 타입 체크가 자연스러웠다.
- **유연했다.** 원하는 방식으로 코드를 짤 수 있었다. 추상화는 커스텀 훅으로, 상태 관리는 원하는 라이브러리로 선택할 수 있었다.

결국 React를 선택한 이유는 **"내가 문제를 푸는 방식"**과 맞았기 때문이었다.

---

## 내가 좋아하는 방식

한 달간 코드를 짜면서 **내가 좋아하는 것**이 뭔지 조금 더 보였다.

- **추상화**를 좋아한다. 같은 패턴이 반복되면 견디기 힘들다. 공통 로직을 뽑아내고, 재사용 가능하게 만들고, 새 기능을 넣을 때 기존 코드를 건드리지 않게 만드는 게 좋다.

---

## 정작 회사에 들어가 보니 놀라웠던 점

**타입**과 **자동화**를 좋아한다. TypeScript로 타입을 정의하고, 워크플로우를 자동화하고, 설정을 중앙에서 관리하는 걸 선호한다. 실수를 줄이고 싶고, 반복 작업을 자동화하고 싶다.


---

## 배운 것

- **도구는 수단**일 뿐이다. Vue를 배우든 React를 배우든, 먼저 물어야 할 건 **"왜?"**다.
- **왜 이 도구를 쓰는가?** 이 도구가 **내 문제**를 어떻게 해결해 주는가? **내 작업 방식**과 맞는가?
- 회사 첫 달에 배운 가장 큰 교훈이다. 아직 모르는 게 많지만, 적어도 **질문하는 법**은 조금 배운 것 같다.

---

## Vue를 왜 쓰는지 서칭해 본 결과

1. **쉽다.** React와 지원하는 기능은 비슷한데 **학습 곡선**이 완만하다. SSR도 되고(Nuxt.js), 대규모로 확장도 잘 된다. 결국 **문법만 다를 뿐**이다.
2. **"Right way"가 있다.** 코드를 짤 때 **정해진 방식**이 있다. 구조, Options API·Composition API 같은 **명확한 가이드**. 선택지가 적어서 팀 내 **컨벤션**을 따로 정할 필요가 적다.
3. **렌더링이 빠르다**는 평가가 있다. React와 성능 차이가 크진 않지만 Vue가 **조금 더 가볍다**는 말이 많다.
4. **업데이트**가 꾸준하다. Vue 3 메이저 이후에도 계속 관리되고 있다.

결국 Vue를 쓰는 이유는 **"정해진 방식으로 빠르게 개발하고 싶을 때"**였다.  
React처럼 **자유도**가 높으면 선택의 폭이 넓지만, 그만큼 **팀 내 논쟁**도 많아진다. Vue는 그 논쟁을 **줄여 준다**.

이제야 이해됐다. 도구를 선택하는 건 **"뭐가 더 좋으냐"**가 아니라 **"우리 팀이 어떻게 일하고 싶으냐"**의 문제였다.
