## 왜 공부하게 되었나?

React, Next.js 프로젝트를 하면서 **"SSR이 더 좋다던데?"**, **"CSR은 SEO에 안 좋다는데?"** 같은 말을 자주 들었다.  
하지만 **어떤 차이가 있는지**, **어떤 상황에서 어떤 방식을 써야 하는지**는 막연했다.  
그래서 SSR과 CSR을 직접 비교해서 장단점을 정리해보기로 했다.

---

## 문제 상황

프로젝트를 진행하다 보니 **화면 로딩 속도**, **SEO**, **페이지 이동 경험**이 서비스 성격에 따라 중요도가 달랐다.

> 예를 들어,
> - **모임 카드 목록**처럼 검색·공유가 중요한 서비스라면 **SEO**와 **초기 로딩 속도**가 핵심 → SSR 필요성 ↑
> - **마이페이지**처럼 로그인 이후 자주 머무르고 상호작용하는 공간이라면 **페이지 전환 경험**(빠른 이동)과 **부드러운 인터랙션**이 핵심 → CSR 필요성 ↑

이 차이를 제대로 이해하지 못한 채 기술만 적용하려다 보니 혼란이 있었다.  
그래서 **"SSR vs CSR, 각각이 무엇이고 어떤 특성을 가지는가?"**를 명확히 정리할 필요가 있었다.

---

## 공부한 내용

### MPA vs SPA

렌더링 방식을 보기 전에, **MPA와 SPA**를 먼저 짚는 이유는 둘 다 **렌더링 방식**과 연결되기 때문이다.

- **MPA(Multi-Page Application)**: 여러 페이지로 이루어져 있어, **변경이 있을 때마다 서버에 페이지를 요청**해 새로 렌더링한다.
- **SPA(Single-Page Application)**: 하나의 페이지로 이루어져 있어, **바뀌는 부분에 대해서만 데이터를 요청**해 렌더링한다.

여기서 **"변경 시마다 서버에 페이지 요청"**과 **"갱신되는 부분만 데이터 요청"**에 집중하면, 각각 **SSR**과 **CSR**과 연결된다는 걸 알 수 있다.

---

### 먼저 정리할 지표

- **TTFB(Time To First Byte)**: 요청을 보내고 **응답의 첫 번째 바이트**가 도착할 때까지의 시간
- **FCP(First Contentful Paint)**: 사용자가 화면에서 **콘텐츠를 처음 볼 수 있는** 시점
- **TTI(Time To Interact)**: 사용자가 **페이지와 상호작용할 수 있게** 되는 시점
- **TBT(Total Blocking Time)**: FCP ~ TTI 사이의 시간 (메인 스레드가 블로킹되는 구간)

---

### CSR (Client-Side Rendering)

- **클라이언트**에서 렌더링을 담당한다.  
  첫 로딩 시 **빈 HTML**을 받고, 필요한 **번들(JS)**을 모두 받은 뒤에 화면을 그린다.
- 흐름: 사용자 접속 → 브라우저가 서버에 리소스 요청 → 서버가 **빈 HTML** 전달 → 브라우저가 JS 다운로드·실행 → 사용자에게 페이지 표시

![CSR 로딩 흐름](/assets/img/41.png)

- **TTFB**는 좋고, **FCP**는 상대적으로 나쁘다. (콘텐츠가 보이기까지 JS 실행을 기다려야 함)

![CSR – TTFB 좋음, FCP 상대적으로 느림](/assets/img/42.png)

| 구분 | 내용 |
|------|------|
| **장점** | 화면 깜빡임 없음, 초기 로딩 이후 전환·인터랙션 속도가 빠름 |
| **단점** | SEO 불리, 초기 로딩이 느릴 수 있음 |

---

### SSR (Server-Side Rendering)

- **서버**에서 렌더링할 페이지를 그려서 **HTML**을 만들어 클라이언트로 내려준다. 요청이 오면 그때그때 HTML을 만든다.
- 흐름: 사용자 접속 → 브라우저가 서버에 요청 → 서버가 **초기 콘텐츠가 들어간 HTML** 전달 → 브라우저가 JS 다운로드 → **하이드레이션** 후 인터랙티브한 페이지 제공

![SSR 로딩 흐름](/assets/img/43.png)

- **FCP**는 좋고, **TBT**는 상대적으로 나쁠 수 있다. (서버에서 그린 HTML은 빨리 보이지만, 클라이언트에서 JS가 실행되기 전까지는 상호작용 불가)

![SSR – FCP 좋음, TBT 주의](/assets/img/44.png)

| 구분 | 내용 |
|------|------|
| **장점** | 초기 로딩·FCP가 좋음, SEO에 유리 |
| **단점** | 페이지 이동 시 깜빡임 가능, 요청마다 서버에서 렌더링해 서버 부하 증가 가능 |

---

## 결과

이번에 정리하면서 **"SSR이 빠르다, CSR이 느리다"** 같은 단순 구분이 아니라, **서비스 성격과 목적**에 따라 적합한 방식이 달라진다는 걸 다시 느꼈다.

- **마이페이지**처럼 SEO는 거의 필요 없고, 로그인 후 **잦은 이동·상호작용**이 중요한 곳은 **CSR**이 더 자연스러웠다.
- **블로그·게시글**처럼 **검색 노출**이 중요한 곳은 **SSR**이 더 맞았다. (단, 블로그처럼 내용이 자주 안 바뀌면 **SSG**가 더 적합할 수 있다.)

즉, **"어떤 게 더 낫다"**가 아니라 **"어떤 상황에서 어떤 방식을 선택할 것인가"**가 핵심이었다.

Next.js 같은 프레임워크는 **SSR과 CSR을 페이지·경로별로 섞어 쓸 수** 있기 때문에, 기술 자체를 아는 것보다 **맥락에 맞게 고르는 판단**이 더 중요하다고 느꼈다.
