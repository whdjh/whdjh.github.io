## 왜 공부하게 되었나?

- **SSR**은 모든 데이터가 준비될 때까지 **한 번에** 전송되어, 느린 구간 하나가 **전체 LCP**를 끌어올린다.
- **Streaming SSR**은 준비된 청크부터 흘려보내 **체감 속도**를 올리지만, **매 요청마다 서버 렌더**가 필요하다.
- **PPR**은 라우트를 **정적 쉘**(사전 프리렌더, 캐시/CDN) + **동적 홀**(요청 시 스트리밍)로 나누어 **TTFB/FCP/LCP**를 더 안정적으로 만든다.

## 공부 내용

### 원리

- **빌드/재검증 시** **정적 쉘** 생성 → **요청 시** 정적 쉘을 **즉시 전송**한 뒤, **Suspense** 경계 안의 **동적 조각**들을 **병렬 스트리밍**한다.

### 장점

- **정적 부분**은 **CDN 캐시**로 초기 표시가 매우 빠르다.
- **동적·개인화** 영역은 그대로 유지된다.
- **한 라우트**에서 **정적 + 동적**을 함께 쓸 수 있다.

## 결과

### 적용 결과

![PPR 적용 결과](/assets/img/65.gif)

### 측정 조건

- **Chrome DevTools Lighthouse** / Navigation / Device: Desktop / **Performance만** 체크
- 각 시나리오 **5회 측정** → **중앙값** / 매 회 하드 리로드

### PPR 성능 측정

- **FCP**: 0.2s로 매우 빠름. 정적 쉘이 **캐시/CDN**에서 즉시 응답되어 첫 화면이 바로 보임.
- **LCP**: 중앙값 0.4s(매우 우수). 5회 모두 0.4s로 안정적. (초기 설정 미적용 때 1회 2.3s 스파이크 있었으나 설정 적용 후 해소)
- **TBT**: 중앙값 480ms. SSR 1.85s → 0.48s로 대폭 감소. 다만 Streaming(420ms) 대비 +60ms 정도로 미세하게 불리.
- **Speed Index**: 0.2s, **CLS**: 0. 화면 완성 속도가 빠르고 시각적 안정성 유지.

### SSR / Streaming SSR / PPR 비교

![SSR vs Streaming vs PPR 비교](/assets/img/66.png)

### 비교 요약

- **SSR → PPR**: FCP −75%, LCP −79%, TBT −74%, Speed Index −92%.
- **Streaming → PPR**: 지표는 대체로 동일. **TBT만 +60ms(+14%)**로 약간 불리.
  1. 이번 테스트는 **간단한 페이지 + 데스크톱**이라 Streaming만으로도 상한에 근접했다.
  2. **대형 페이지 / 모바일 / 네트워크 제약**에서는 PPR의 **캐시·CDN 기반 TTFB 안정화**가 더 크게 드러난다.

### 해석

FCP, LCP, Speed Index는 **Streaming과 동급**이다. **TBT**는 약 60ms 높음(420→480ms). 경계·JS 분할에 따른 **미세 차이** 수준이다.
