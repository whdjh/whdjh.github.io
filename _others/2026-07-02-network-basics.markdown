## HTTP 메시지 구조

HTTP 메시지는 클라이언트와 서버가 주고받는 데이터 단위다.  
기본 구조는 `메시지 헤더`, `개행 문자(CR+LF)`, `메시지 바디`로 나뉜다.

```txt
HTTP 메시지
┌──────────────────────────────┐
│          메시지 헤더          │
├──────────────────────────────┤
│       개행 문자(CR+LF)        │
├──────────────────────────────┤
│          메시지 바디          │
└──────────────────────────────┘
```

- **메시지 헤더**: 요청이나 응답에 대한 부가 정보를 담는다.
- **개행 문자(CR+LF)**: 헤더와 바디를 구분한다.
- **메시지 바디**: 실제 주고받는 데이터를 담는다.

---

## 메시지 헤더 구조

메시지 헤더는 `상태 라인`, `HTTP 헤더 필드`, `그 외`로 나눌 수 있다.  
HTTP 헤더 필드는 다시 `리스폰스 헤더 필드`, `일반 헤더 필드`, `엔티티 헤더 필드`로 구성된다.

```txt
메시지 헤더
┌──────────────────────────────┐
│ 상태 라인                       │  HTTP 버전, 상태 코드
├──────────────────────────────┤
│ 리스폰스 헤더 필드                │
│ 일반 헤더 필드                   │  HTTP 헤더 필드
│ 엔티티 헤더 필드                 │
├──────────────────────────────┤
│ 그 외                         │
└──────────────────────────────┘
```

- **상태 라인**: HTTP 버전과 상태 코드를 가진다.
- **리스폰스 헤더 필드**: 응답 메시지에 대한 부가 정보를 담는다.
- **일반 헤더 필드**: 요청과 응답에서 공통으로 사용할 수 있는 정보를 담는다.
- **엔티티 헤더 필드**: 메시지 바디의 형식, 길이 같은 정보를 담는다.
- **그 외**: 위 항목에 속하지 않는 기타 정보다.

## 리퀘스트 메시지 구조

리퀘스트 메시지는 클라이언트가 서버로 보내는 HTTP 메시지다.  
메시지 헤더는 `리퀘스트 라인`, `HTTP 헤더 필드`, `그 외`로 나눌 수 있다.

```txt
메시지 헤더
┌──────────────────────────────┐
│ 리퀘스트 라인                    │  메소드, URI, HTTP 버전
├──────────────────────────────┤
│ 리퀘스트 헤더 필드                │
│ 일반 헤더 필드                   │  HTTP 헤더 필드
│ 엔티티 헤더 필드                 │
├──────────────────────────────┤
│ 그 외                         │
└──────────────────────────────┘
```

- **리퀘스트 라인**: 메소드, URI, HTTP 버전을 가진다.
- **리퀘스트 헤더 필드**: 요청 메시지에 대한 부가 정보를 담는다.
- **일반 헤더 필드**: 요청과 응답에서 공통으로 사용할 수 있는 정보를 담는다.
- **엔티티 헤더 필드**: 메시지 바디의 형식, 길이 같은 정보를 담는다.
- **그 외**: 위 항목에 속하지 않는 기타 정보다.

## HTTPS 통신 흐름

HTTPS는 HTTP 메시지를 그대로 보내지 않고, TLS를 통해 암호화해서 주고받는다.  
이를 위해 서버는 먼저 인증 기관(CA)을 통해 공개키 증명서를 준비한다.

```txt
서버 공개키 등록
→ 서버의 공개키를 인증 기관에 등록
→ 인증 기관이 서버 공개키에 디지털 서명
→ 공개키 증명서 발급
→ 브라우저는 인증 기관의 공개키로 증명서를 검증(공개키 증명서: 서버의 공개키 + 인증 기관의 디지털 서명)
→ 검증된 서버 공개키로 안전한 통신 준비
```

- **서버의 공개키**: 클라이언트가 서버로 안전하게 정보를 보내기 위해 사용한다.
- **서버의 비밀키**: 서버만 가지고 있으며, 공개키로 암호화된 정보를 복호화할 때 사용한다.
- **인증 기관의 디지털 서명**: 이 공개키가 진짜 서버의 공개키인지 확인하는 근거가 된다.

이후 클라이언트와 서버는 TLS 핸드셰이크를 통해 암호화 통신에 필요한 정보를 주고받는다.

```txt
클라이언트                                      서버
   │                                            │
   │ Handshake: ClientHello                     │
   │ ─────────────────────────────────────────> │
   │                                            │
   │ Handshake: ServerHello                     │
   │ <───────────────────────────────────────── │
   │ Handshake: Certificate                     │
   │ <───────────────────────────────────────── │
   │ Handshake: ServerHelloDone                 │
   │ <───────────────────────────────────────── │
   │                                            │
   │ Handshake: ClientKeyExchange               │
   │ ─────────────────────────────────────────> │
   │ ChangeCipherSpec                           │
   │ ─────────────────────────────────────────> │
   │ Handshake: Finished                        │
   │ ─────────────────────────────────────────> │
   │                                            │
   │ ChangeCipherSpec                           │
   │ <───────────────────────────────────────── │
   │ Handshake: Finished                        │
   │ <───────────────────────────────────────── │
   │                                            │
   │ Application Data(HTTP)                     │
   │ ─────────────────────────────────────────> │
   │ Application Data(HTTP)                     │
   │ <───────────────────────────────────────── │
   │                                            │
   │ Alert: warning, close notify               │
   │ ─────────────────────────────────────────> │
```

핸드셰이크가 끝나면 그때부터 실제 HTTP 데이터가 암호화되어 오간다.  
즉 HTTPS는 HTTP 자체가 완전히 다른 프로토콜이 되는 것이 아니라, HTTP 메시지를 TLS 위에서 안전하게 주고받는 방식이다.
