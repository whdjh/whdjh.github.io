## 개요

Swagger가 API 타입을 자동으로 생성하듯, **번역 파일이 자동으로 다국어 리소스를 생성**하고 프론트엔드 개발자는 이를 사용하기만 하는 구조를 지향한다.

유지보수 효율성과 협업 편의성을 최우선 기준으로 하여 툴을 선정하고 책임을 분리한다.

---

## 평가 기준

### 핵심 요소

- **비용:** 유료/무료 여부 및 향후 확장성
- **중복성:** 중복 단어·키 처리 능력
- **추적성:** 수정 사항 히스토리(History) 추적 가능 여부
- **연동성:** Github 연동 및 CI/CD 자동화 용이성
- **CRUD:** 생성(Create), 읽기(Read), 수정(Update), 삭제(Delete) 편의성
- **편의성:** 비개발자(기획자/번역가)의 사용 익숙함

### 추가 요소

- **Key 네이밍:** 계층 구조(Depth) 관리 전략
- **운영 안정성:** 배포 시간, 동시성 제어, 롤백(Rollback) 시나리오

## 후보군 상세 분석

### 1순위: 백오피스

- **Workflow:** 백오피스 어드민에서 수정 → 저장 시 자동 반영 워크플로우(API 호출 / Github Commit) 실행
- **분석 코멘트:**
  - **기능적 완결성:** 개발자가 의도한 대로 검증 로직(중복 체크, Key 네이밍 규칙 등) 및 프로세스 구현이 가능하다.
  - **보안 및 안정성:** 회사 내부 보안·인프라 정책에 맞춘 관리가 가능하다.
  - **확장성:** 서비스 특성에 맞는 기능을 자유롭게 추가할 수 있다.

### 2순위: Google Sheets

- **Workflow:** 구글 시트에 번역 데이터 입력 → Apps Script로 JSON 생성·검증 → Github 자동 Commit & Push
- **분석 코멘트:**
  - **CRUD & 편의성:** 엑셀과 동일한 UX로 교육 없이 데이터 조작이 가능하다.
  - **이력 추적:** 셀 단위 수정 기록 표시 및 복구가 용이하다.
  - **구조 관리:** 열(Column) Depth로 Key 네이밍 구조를 잡을 수 있다.
  - **단점:** 연동용 스크립트 작성·유지보수 비용이 발생한다.

### 3순위: Slackbot (탈락 후보)

- **Workflow:** 명령어 입력 → 봇 처리 → Github Commit & 알림
- **분석 코멘트:**
  - 모바일 접근성은 뛰어나다.
  - 전체 데이터 조회·관리를 위해 **별도 페이지(백오피스 등)가 필요해 이중 작업**이 된다.
  - 초기 셋팅 복잡도가 높다.

### 4순위: Notion DB

- **Workflow:** 노션 표 입력 → API 호출 워크플로우
- **분석 코멘트:**
  - 기획자에게 익숙하고 가독성이 좋다.
  - **치명적 단점:** 입력 단계에서 데이터 검증(중복, 오타, Key 규칙 등)이 없어 **휴먼 에러 제어가 불가능하다.**

### 5순위: Inlang

- **Workflow:** 웹 에디터 접속 → 수정·저장 → Github Commit 자동 생성 → paraglide 반영
- **분석 코멘트:**
  - `Create` 기능이 불안정하다.
  - 특정 라이브러리(`paraglide`)를 강제로 써야 하는 **강한 종속성**이 있다.
  - 입력 단계 데이터 검증이 미흡하다.

## 결론 및 가이드라인

**최종 결정: 백오피스(Backoffice) 채택**

운영 안정성과 데이터 무결성을 최우선으로 **백오피스 자체 구축**을 1순위로 진행한다.

1. **개발 자유도:** 중복성 체크, Key 네이밍 규칙 등 비즈니스에 맞는 검증 시스템을 탑재한다.
2. **안전성:** 휴먼 에러를 시스템 차원에서 막고, 배포·롤백 프로세스를 내부 인프라와 통합한다.
3. **협업:** 기획자/번역가는 백오피스 UI로 리소스를 관리하고, 개발자는 자동 생성된 리소스를 사용하기만 하는 구조를 만든다.
